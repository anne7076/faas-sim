1. Pluggable Policy Interface (WorkflowScheduler)

All workflow scheduling policies inherit from WorkflowScheduler (sim/workflow/scheduler.py) and implement:

Three policies are implemented to represent distinct scheduling philosophies:

  1. RoundRobinWorkflowScheduler: Baseline topology- and data-agnostic policy. Reuses idle warm replicas in round-robin order when available, and scales out across feasible nodes using a persistent counter.
  2. DataAwareWorkflowScheduler: Pure data-locality policy (analogous to SAND / VM-Storage preference). Minimizes total incoming data transfer latency ∑u∈parents(v)​Ttransfer​(nu​→n) with warm-replica preference and optional load-balancing weight.
  3. MakespanWorkflowScheduler: Critical-path completion-time optimizer (inspired by SONIC [4] and Skippy [3]). Jointly trades off network transfer time, link contention, cold-start/image locality, hardware compute speedup, and multi-tenant node contention.

2. How DataAwareWorkflowScheduler Works

DataAwareWorkflowScheduler (sim/workflow/scheduler.py) is a data-locality-first policy (analogous to SAND’s locality preference). It filters feasible nodes via Skippy predicates (and an optional max_tasks_per_node cap using ancestor-excluded active load), then splits into two cases:

2.1 Root Tasks (parents(v)=∅)

Because a root task has no incoming data dependencies, DataAwareWorkflowScheduler selects a node n∈Eligible(v) by minimizing the lexicographic tuple:
(I(n∈/Feasible(wmax​)),ColdPenalty(v,n),ActiveLoad(n))

  1. Downstream Co-locatability (E-1): Prefers nodes that can also host the heaviest outgoing child wmax​ (so the subsequent edge can collapse to zero-hop COLOCATED).
  2. Replica Warmth: Prefers nodes already hosting a warm replica of v.
  3. Active Load: Breaks ties by lowest concurrent non-ancestor task count.

2.2 Dependent Tasks (parents(v)=∅)

For each candidate node n∈Eligible(v), DataAwareWorkflowScheduler minimizes:
ScoreDA​(n)=wnet​⋅u∈parents(v)∑​T^transfer​(nu​→n,sizeu,v​,modeu,v​)+wload​⋅ActiveLoad(n)+ColdPenalty(v,n) where:

  • Sum of Incoming Transfers (∑): Accumulates estimated transfer time across all incoming edges (weighted by network_weight, default 1.0).
  • Optional Load Penalty: load_balance_weight * ActiveLoad(n) (default 0.0, i.e., pure data locality unless explicitly enabled).
  • Flat Cold-Start Penalty: Adds a fixed cold_start_penalty (default 0.5s) when warm replicas exist elsewhere and n∈/Warm(v) (does not model image layer pull times).
  • No Compute-Speed Model: Treats all hardware tiers (rpi3, nuc, tx2, server) as having identical compute speed. Consequently, for compute-heavy tasks with small payloads, it stays on a slow rpi3 to avoid a tiny transfer rather than offloading to a faster server.

3. The 5 Criteria of MakespanWorkflowScheduler

For a ready task v and each candidate node n∈Feasible(v), MakespanWorkflowScheduler minimizes:

Score(n)=Ttransfer​(v,n)+Tcold​(v,n)+Tcompute​(v,n)+Tlookahead​(v,n)

Criterion 1: Skippy Hardware Predicate Feasibility (Feasible(v))

  • Filters out switches, container registries, and storage-only nodes.
  • Evaluates env.scheduler.passes_predicates(probe_pod, s_node) without mutating global pod counters (_build_probe_pod), ensuring CPU, RAM, architecture (arm32, aarch64, x86), and capability labels are satisfied.

Criterion 2: Critical-Path Incoming Data Transfer & Sibling Link Contention (Ttransfer​(v,n))

Ttransfer​(v,n)=u∈parents(v)max​T^flow​(nu​→n,sizeu,v​,ke​)

  • Uses maxu∈parents(v)​ (rather than ∑) because incoming transfers from multiple completed parents run concurrently (simpy.AllOf).
  • Divides link bandwidth Be​ by 1+ke​, where ke​ is the number of already-placed concurrent sibling transfers from the same parent u traversing link e (matching SONIC Equations 3–4 and Ether’s max-min fair flow allocation).

Criterion 3: Replica Warmth & Container Image Locality (Tcold​(v,n))

Tcold​(v,n)=⎩⎨⎧​0τbase​τbase​+T^flow​(Registry→n,0.1×Simg​)​if n∈Warm(v)if n∈/Warm(v) and image cached on nif image not cached on n​

  • Follows Skippy ([3] Section 4.5), where 90% of container base layers are shared across images and 10% of the image size represents unique function layers pulled from DockerRegistry.

Criterion 4: Heterogeneous Compute Speed & Active Contention (Tcompute​(v,n))

Tcompute​(v,n)=dbase​(v)×CPUeff​(n)CPUref​​×(1+α⋅ActiveLoad(n))

  • 4-Tier Hardware Speedup (compute_node_speedup_ratio):
    • rpi3 (sbc, ARM Cortex-A53): 0.5× reference speed (2,000m effective).
    • nuc (sffc, Intel Core i5): 1.0× reference speed (4,000m effective).
    • tx2 (embai, NVIDIA Jetson TX2 CUDA): 1.5× reference speed (6,000m effective).
    • server (Xeon 88-core cloudlet): 4.0× single-container core cap (16,000m effective).
  • Ancestor-Excluded Contention (ActiveLoad(n)): Excludes completed ancestor tasks in the DAG (_get_ancestors) so sequential parent pods sitting idle on node n are never mistaken for active CPU contention, while counting parallel non-ancestor tasks and active in-flight requests.

Criterion 5: Root-Task Downstream Co-location Lookahead (Tlookahead​(v,n))

  • When v is a root task (parents(v)=∅) with a heavy outgoing edge (v→w), if candidate node n∈/Feasible(w) (e.g., n is a 1 GB rpi3 that cannot host a 1024 MiB resnet50-inference child), adds minm∈Feasible(w)​T^transfer​(n→m) so the scheduler accounts for the unavoidable hop forced on child w.

Critical Assessment: Are All 5 Criteria Relevant?

Every criterion directly prevents a distinct failure mode observed in edge-cloud workflows.

Transfer + Sibling Link SharingWithout transfer cost, tasks scatter across WAN links (RoundRobin); without sibling link-sharing (ke​), fan-out stages send all K parallel branches over a single 25 Mbps WAN uplink to cloud servers (6.95s vs. 3.13s).Experiment 2 (1 MB → 50 MB) & Experiment 3 (K=1→8)
